## 一、题目背景

AI 开发助手修改代码时，需要知道当前应遵守哪些要求、应该修改哪些代码，以及如何验证结果。资料分散、规格变化或任务中断，都可能导致遗漏约束、使用过时信息或重复工作。

本题要求参赛者围绕规格驱动开发（Spec-Driven Development，SDD），实现一个工程上下文模块：根据开发任务找到适用的规格、相关代码和测试，保存任务进展，并通过实际代码修改验证模块的作用。

可以复用已有业务工程、开发 Agent 和 SDD 工具，无需从零开发完整 Agent 框架。

## 二、题目内容

### 2.1 完成一次开发任务

选择一个能够运行、具有测试的业务工程，定义并完成一项局部修改，例如增加筛选条件、修复边界输入，或调整接口行为。

作品必须完成以下流程：

1. 导入任务涉及的规格、代码和测试资料。
2. 根据任务选择相关资料，形成开发上下文。
3. 将上下文提供给使用 MiniMax 的开发助手，完成代码修改。
4. 运行功能与回归测试，验证修改结果。
5. 保存任务状态，重新启动上下文模块后读取并使用该状态。

验证样例需明确“要改什么”和“哪些原有行为必须保持”。仅输出方案、检索结果或规格文档，不满足任务要求。

### 2.2 技术结合要求

| 技术                | 必须承担的作用                                       |
| ------------------- | ---------------------------------------------------- |
| MiniMax             | 参与本次任务的代码生成或修改                         |
| seekdb 或 OceanBase | 存储工程资料或索引，查询、检索结果用于构造任务上下文 |
| PowerContext        | 保存任务进展或验证结果，并在后续运行中读取、使用     |

接入方式不限，可以使用 SDK、HTTP API、MCP 或插件。运行说明中应注明实际采用的方式和版本。

指定技术必须参与上述任务流程。仅安装组件、测试连接或在文档中提及名称，不满足要求。业务工程原有的数据库可以保留。

### 2.3 上下文模块要求

模块应提供明确的调用入口，并说明输入与输出。CLI、HTTP API、MCP 工具和 Agent 插件均可。

针对验证样例，输出应能定位：

+ 本次任务适用的规格条目。
+ 需要修改的代码文件或符号。
+ 用于验证功能及兼容性的测试。
+ 已完成事项、待办事项和已有验证结果。

输出中的来源必须真实存在。更新样例中的规格并重新导入后，模块应使用更新后的内容，不能始终返回固定答案。

### 2.4 扩展能力

鼓励展示规格变更处理、跨会话任务恢复、跨模块协作，以及成本或时延优化。这些能力不属于本题必做项，不另行加分。

其中，基础要求中的“任务状态复用”只要求模块重启后能够读取并使用保存的状态，不要求恢复完整 Agent 会话。

作品材料放在参赛仓库的 `minimax/` 目录。评审以平台记录的固定提交为准。

| 材料         | 要求                                                              |
| ------------ | ----------------------------------------------------------------- |
| 完整源码     | 上下文模块、Agent 接入代码及运行所需的配套程序                    |
| 运行说明     | 依赖版本、配置步骤、数据初始化、调用入口、测试命令及已知限制      |
| 验证样例     | 任务描述、有效规格、初始数据、操作步骤、预期结果及重置方法        |
| 代码与测试   | 修改前后代码快照、代码差异、新增功能测试、相关回归测试及运行日志  |
| 技术使用记录 | MiniMax 开发记录、数据库查询记录、PowerContext 状态写入与复用记录 |
| 一页技术说明 | 模块结构、上下文选择方式和各项技术的分工                          |

验证样例应列明上下文中必须包含的规格、代码和测试来源，便于评审核对。测试日志需记录命令、退出码和对应代码版本。

截图、录屏可以作为补充，不能替代源码和复现步骤。复用开源代码或数据时，注明来源及修改内容。配置示例使用占位值，不提交真实凭据，不要求提交模型私有思维链。

## 四、评分与测试

### 4.1 必做项

以下六项全部通过，得 20 分；任一项不通过，得 0 分。

| 验收项           | 通过条件                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------- |
| 能够运行         | 按运行说明可以初始化数据、启动模块并执行验证样例，不依赖未交付的本地文件或状态           |
| MiniMax 实际参与 | 开发记录包含本次任务、提供的上下文和代码修改过程，并与提交的代码差异对应                 |
| 上下文正确       | 输出包含样例规定的必要规格、代码和测试来源；规格更新并重新导入后，输出使用更新内容       |
| 数据库实际参与   | seekdb／OceanBase 中保存了工程资料或索引，实际查询结果用于任务上下文                     |
| 状态能够复用     | 从空状态开始保存任务记录，重启模块后能够读取，并用于后续上下文或任务处理                 |
| 代码修改有效     | 同一组目标功能测试在修改前因目标行为未实现而失败，修改后全部通过；相关回归测试也全部通过 |

目标测试不能以缺少依赖、无法启动等环境错误充当修改前的功能失败。

界面美观、代码量、提交次数和扩展能力均不替代上述条件，也不额外计分。

### 4.2 验收方式

评审从干净环境开始，按提交说明依次验证模块运行、上下文输出、数据库使用、状态复用和代码测试，并核对 MiniMax 开发记录。

代码结果以评审实际执行的测试为准。测试集在修改前后保持一致，不得通过删除断言、跳过测试或修改预期结果使其通过。

MiniMax 的使用通过开发记录核对，不要求模型重新生成完全相同的补丁。上下文输出按必要内容和来源核对，不要求措辞或排序完全一致。

补充测试只能检查题面已声明的行为，不能增加未公开的要求。每个未通过项须记录实际结果和失败原因。

因作品材料不完整导致无法验证，记为对应验收项不通过；因平台或裁判环境故障导致无法评测，修复后重新执行，不直接判为作品不通过。
