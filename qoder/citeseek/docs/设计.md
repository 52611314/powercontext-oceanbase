# CiteSeek 设计说明

## 1. 定位

面向研究生、本科生和科研工作者的文献与资料检索工作台。解决的痛点是：资料散落在论文、课件和笔记里，用关键词找不到、用语义搜不准、找到了又不知道出自哪一页。

核心闭环：**导入 → 解析切块 → 混合索引 → 检索/问答 → 回到原文那一页**。

## 2. 架构

```
┌────────────── app 容器 (FastAPI) ──────────────┐
│ 上传 → pypdf/文本解析 → 句级切块 → ONNX 嵌入    │
│ 检索 API → 混合召回 → RRF 融合 → 高亮 / 引用    │
└───────────────┬────────────────────────────────┘
                │ MySQL 协议
        ┌───────▼────────┐
        │ seekdb 容器     │
        │ HNSW + FULLTEXT│
        └────────────────┘
```

- 内容平面全部放在 seekdb：文档元数据、页文本、块文本与向量、检索历史、收藏。
- 嵌入在应用进程内完成，模型随仓库内置，评审环境不需要联网下载。

## 3. 数据模型

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `documents` | 文献元数据与索引状态 | id, title, sha256, status, progress, tags, read_status |
| `pages` | 页级原文 | doc_id, page, section, text |
| `chunks` | 检索单元 | id, doc_id, page, section, text, char_start, char_end, embedding VECTOR(512) |
| `searches` | 检索历史（含实际耗时与通道） | query, filters, latency_ms, channels |
| `favorites` | 收藏的片段 | chunk_id, note |

索引：`FULLTEXT INDEX ft_text(text) WITH PARSER ik`、`VECTOR INDEX vidx_emb(embedding) WITH (distance=cosine, type=hnsw, lib=vsag)`。

## 4. 关键决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| seekdb 部署方式 | 服务端容器 + MySQL 协议 | 评审可用任意客户端查库；EXPLAIN 可直接核对 `TEXT RETRIEVAL SCAN` 与 `VECTOR INDEX SCAN` |
| 中文分词 | seekdb 内置 IK | 免去 jieba 预分词与词典维护 |
| 嵌入模型 | bge-small-zh-v1.5 int8 ONNX | 24MB 可随仓库分发；实测排序与 fp32 一致 |
| 文本文件分页 | Markdown 按标题切「页」 | 与 PDF 页码统一，前端只需一种出处模型 |
| 切块 | 句级、目标 420 字、重叠 80 字、不跨页 | 保证引用可回溯到具体页，且语义完整 |
| 出处展示 | 页文本视图 + 原文 PDF `#page=N` | 不做 pdf.js，省两天且不影响可追溯性 |

## 5. 检索设计（下一阶段）

单条 SQL 内完成两路召回：

```sql
WITH fts AS (
  SELECT id, doc_id, page, text, MATCH(text) AGAINST(%s IN NATURAL LANGUAGE MODE) AS score
  FROM chunks WHERE MATCH(text) AGAINST(%s IN NATURAL LANGUAGE MODE)
  ORDER BY score DESC LIMIT 50
), vec AS (
  SELECT id, doc_id, page, text, COSINE_DISTANCE(embedding, %s) AS dist
  FROM chunks ORDER BY dist APPROXIMATE LIMIT 50
)
SELECT 'fts' AS channel, ... FROM fts
UNION ALL
SELECT 'vector', ... FROM vec
```

融合使用 RRF（k=60），同时保留两路原始分数用于调试面板。过滤条件（doc_ids / tags / 年份）同时下推到两个分支。

## 6. 证据设计

评审可以按以下顺序核对 seekdb 的实际作用：

1. UI 的「检索证据」抽屉展示本次执行的 SQL、EXPLAIN、两路候选与耗时；
2. `logs/retrieval.jsonl` 逐条记录查询、通道、命中；
3. `docker compose exec seekdb mysql -uroot -e "SELECT ..."` 直接查 `chunks` 表；
4. `scripts/probes/probe_e2e.py` 是最小可复现探针，独立于业务代码。
