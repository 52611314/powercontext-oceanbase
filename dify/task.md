## 一、题目背景

一个会记住玩家恶作剧的 NPC，一场由 AI 主持的脑洞辩论，一段越聊越离奇的冒险故事……智能应用可以从一个让人想试试的点子开始。

本题以 Just for Fun 为主题，鼓励参赛者自由发挥，使用 Dify，结合 seekdb 或 PowerContext，做一个有趣、可以体验的智能应用。选题不限，重点是把创意做出来，让别人也能上手玩。

## 二、题目内容

### 2.1 做一个可以体验的作品

参赛者自主设计应用的主题、玩法或互动方式，说明作品有什么好玩的、用户如何参与，并实现从输入、互动到反馈的完整体验。作品可以是小游戏、创作工具、角色互动，也可以是其他有趣的尝试。

应用可以采用 Dify Workflow、Chatflow 等形式，也可以结合工具调用或配套后端。允许使用 Dify 提供的应用界面或 API 作为入口，无需另行开发独立前端。是否使用自定义插件、额外服务或更复杂的流程，由应用需求决定。

### 2.2 技术结合要求

| 组成                         | 要求与作用                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| Dify（必选）                 | 承担应用的核心流程编排，例如输入处理、模型调用、检索或工具调用、条件判断和结果输出；提交对应的 DSL       |
| seekdb（至少选择一种）       | 作为 Dify 部署时使用的数据库，或为应用提供数据存储、查询与检索能力，例如素材匹配、设定检索或游戏数据查询 |
| PowerContext（至少选择一种） | 保存并复用应用中的记忆或上下文，例如用户偏好、角色状态、剧情进展和历史互动                               |

**Dify + seekdb、Dify + PowerContext、Dify + seekdb + PowerContext 均符合技术选型要求。** 选择 PowerContext 的作品不额外要求使用 seekdb；同时使用两者的作品应说明各自分工。

**支持使用 seekdb 作为自行部署 Dify 时使用的数据库。** 参赛者应明确 seekdb 承载的是知识库向量存储、应用数据存储或其他数据，并提供支持相应用途的 Dify 版本或适配分支、seekdb 版本及部署配置。只要 seekdb 实际承担所声明的数据存储职责，且应用的主要功能可按说明正常体验，即满足 seekdb 的使用要求，无需在工作流中额外增加直接调用 seekdb 的节点。

seekdb 支持向量、全文及结构化条件结合的检索，可根据场景选择所需能力，参见 [seekdb 项目说明](https://github.com/oceanbase/seekdb)。PowerContext 提供记忆与任务上下文能力，并支持 HTTP API 等接入方式，参见 [PowerContext 接口说明](https://powercontext.oceanbase.io/zh/docs/develop/interfaces/)。

参赛者可复用与所声明版本兼容的插件，也可通过 HTTP API、自定义工具或配套后端完成接入。Dify 的 HTTP Request 节点支持调用外部服务，可用于连接 PowerContext HTTP API，参见 [Dify HTTP Request 文档](https://docs.dify.ai/en/cloud/use-dify/nodes/http-request)与 [PowerContext API 快速开始](https://powercontext.oceanbase.io/zh/docs/develop/api-quickstart/)。运行说明应交代实际采用的接入方式、依赖版本及配置步骤；使用插件时注明具体插件名称与安装来源。

指定技术必须在应用功能或部署运行中实际发挥作用。作为 Dify 部署数据库使用时，应提供部署配置及实际数据读写的验证记录；用于应用功能时，应展示数据或检索结果如何用于互动流程，或者记忆如何被保存并在后续互动中复用。仅安装组件或测试连接，不满足这一要求。

### 2.3 参考方向

以下只是一些玩法示例，欢迎设计自己的作品。技术结合方式可根据作品需要选择。

| 方向               | 玩法示例                                                   |
| ------------------ | ---------------------------------------------------------- |
| 互动剧情与角色扮演 | 玩家用一句话改变故事走向，角色会对之前的选择作出反应       |
| 派对游戏与脑洞挑战 | 让 AI 主持猜谜、接梗或离谱辩论，和朋友一起参与             |
| 创意生成与共创     | 输入几个不搭界的词，和 AI 一起编故事、写台词或设计虚构世界 |
| 个性化虚拟伙伴     | 设计一个性格鲜明的角色，在互动中形成彼此熟悉的习惯和梗     |

### 2.4 公开参考示例

+ [dzh-gitcode/dify-workflows](https://github.com/dzh-gitcode/dify-workflows) 的娱乐游戏目录列有《完蛋！我被 LLM 包围了！》《瞎说新语》等 DSL，可参考互动游戏和趣味文字应用的设计。

这些示例用于启发玩法和实现方式。复用时应核对许可、Dify 版本、模型、插件及外部服务依赖，并按本题要求接入 seekdb 或 PowerContext。参赛作品仍以提交材料中的实际运行结果为准。

## 三、验收标准

### 3.1 基础验收

评审按照提交材料，在作品声明的运行环境中配置依赖、导入 DSL、初始化所需数据并执行验证样例。满足以下条件，即达到基础要求：

1. **能够运行。** DSL 可导入，所需模型、插件、数据和后端可按说明完成配置，应用能够接收输入并返回结果。
2. **能够体验主要功能。** 至少提供一组完整验证样例，包含初始条件、输入、操作步骤和预期表现，评审能够按步骤体验作品的主要玩法或功能。
3. **技术结合有效。** Dify 承担核心流程，seekdb 或 PowerContext 在应用功能或部署运行中实际发挥作用；可以通过数据库部署配置及实际读写记录、节点执行记录、查询结果或记忆读写记录等材料核对其作用。
4. **过程可以复现。** 运行所需的材料和步骤完整，评审无需依赖作者本地已有但未交付的数据、配置或服务状态。

验证样例应与作品声明的能力对应。例如，互动剧情可以展示一次选择如何影响后续发展；具有跨会话记忆的角色可以展示新会话中如何回应之前的互动。开放式创作或游戏无需提供唯一标准答案，说明预期交互、应遵守的规则或输出形式即可。

截图、录屏和运行日志可作为验证材料，但仍需提供可运行的应用和明确的复现步骤。

### 3.2 评价维度

通过基础验收后，可从以下方面评价作品质量：

| 维度               | 关注内容                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------- |
| 创意               | 点子、设定或玩法是否有特色，是否让人想尝试                                                |
| 趣味与互动         | 互动是否有趣，用户的输入或选择是否带来有意思的反馈                                        |
| 体验与完成度       | 玩法是否容易理解，主要流程是否完整、顺畅，作品是否实现了所描述的体验                      |
| 技术结合           | Dify 与 seekdb、PowerContext 的分工是否合理，所用能力是否对应用功能或部署运行产生实际帮助 |
| 工程质量与可复现性 | 配置与部署是否清晰，数据和依赖是否齐全，异常情况是否得到合理处理                          |

具体评分细则、权重、评测环境及资源限制由赛事后续公布。基础验收不预设排名分数，也不以节点数量、插件数量或同时使用两种指定技术作为质量判断依据。

## 四、提交材料

### 4.1 Dify DSL

提交完成应用所需的全部 DSL 文件，并说明各文件的用途和导入顺序。注明适用的 Dify 版本及部署方式；如需重新绑定知识库、工具或服务地址，应写明具体步骤。

### 4.2 运行说明

提供一份运行说明，至少包含：

+ 作品创意、玩法或核心功能、体验方式，以及 Dify 与指定技术的分工。
+ 运行环境、软件和插件版本、所需模型服务及配置项；使用 Embedding 或 Rerank 服务时一并说明。
+ 从安装依赖、导入 DSL、初始化数据到启动应用的完整步骤，以及应用入口。
+ 外部服务的获取和配置方式、Dify 访问服务所需的网络条件、必要的资源条件，以及已知功能限制。

配置示例使用占位值，不提交真实 API Key、密码或其他凭据。复用公开工作流、代码或数据时，注明来源及所作改动。

### 4.3 验证样例与运行证据

至少提交一组可以按步骤执行的完整样例，包括：

+ 初始数据或记忆状态、输入内容和操作顺序。
+ 预期交互、输出形式或主要功能的验证方式。
+ 实际运行结果，以及截图、录屏或日志等证据。
+ seekdb 或 PowerContext 在应用功能或部署运行中的作用及对应记录。

如果样例依赖连续操作，应说明执行顺序及如何恢复初始状态，便于重复验证。

### 4.4 按依赖补充的材料

| 涉及内容              | 应补充的材料                                                                                                   |
| --------------------- | -------------------------------------------------------------------------------------------------------------- |
| 使用 seekdb 部署 Dify | Dify 版本或适配分支、seekdb 版本、数据库用途、部署配置、初始化方式和实际读写验证步骤；涉及适配修改时附对应源码 |
| 知识库或外部数据      | 完成验证样例所需的数据，或可执行的获取、生成与初始化方式；注明数据来源，以及必要的导入、索引和检索配置         |
| 预置记忆或互动状态    | 初始化数据或脚本，说明用户、角色或会话标识如何与工作流关联                                                     |

| 自定义插件            | 可安装的插件包、对应源码、依赖和安装配置说明                                                                   |
| 自定义后端或前端      | 对应源码、依赖清单、配置示例及启动说明；使用镜像或其他构建产物时，注明版本与构建方式                           |
