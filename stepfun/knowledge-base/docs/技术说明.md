# 技术说明（一页）

## 1. 模型与量化

- **模型**：`bge-small-zh-v1.5`（BAAI，512 维，中文检索），ONNX 版本来自 <https://huggingface.co/Xenova/bge-small-zh-v1.5>；
- **量化方案**：
  - INT8：`onnxruntime.quantization.quantize_dynamic(weight_type=QInt8)`，权重动态量化，无需校准集，产物 `model_quantized.onnx`；
  - FP16：官方 FP16 ONNX（自转换在 Cast 节点出现类型不匹配，未采用）；
  - FP32：原始 ONNX，作为质量基线。
- **体积与压缩比**（同一口径，实测字节数）：

  | 精度 | 体积 | 压缩比 |
  | --- | --- | --- |
  | FP32 | 90.46 MB | 1.00x |
  | FP16 | 45.30 MB | 2.00x |
  | INT8 | 22.81 MB | 3.97x |

- **质量变化**（20 篇语料 / 30 条查询 / 人工 qrels，同一浏览器与检索配置）：

  | 配置 | Recall@10 | nDCG@10 | MRR@10 |
  | --- | --- | --- | --- |
  | FP32 基线 | 1.0000 | 0.9186 | 0.8992 |
  | FP16 + WebGPU | 1.0000 | 0.9186 | 0.8992 |
  | INT8 + WASM | 0.9667（-3.3pt） | 0.8860（-3.3pt） | 0.8667（-3.3pt） |

  结论：FP16 相对 FP32 检索质量无损；INT8 下降约 3.3 个百分点，换来 3.97x 体积压缩与更低的查询向量化耗时，属于“质量不明显下降”的可接受区间。

## 2. 端侧运行

- **运行时**：Transformers.js（`@huggingface/transformers`）+ ONNX Runtime Web，推理在 Web Worker 中执行，主线程只负责 UI；
- **WebGPU 选择**：`navigator.gpu.requestAdapter()` 探测，可用时 `device='webgpu'`、`dtype='fp16'`；不可用或 pipeline 初始化抛错时自动回落 `device='wasm'`、`dtype='q8'`，界面徽标实时显示当前后端与降级原因；
- **验证结果**（Edge 156.0.4314.42，headless + CDP 自动化）：
  - WebGPU 路径：徽标 `WebGPU · FP16`，512 维，单条查询向量化 163–178 ms；
  - `--disable-gpu` 路径：`requestAdapter` 返回 null → 徽标 `WASM · Q8`，单条 53 ms，降级提示正常；
- **离线**：`env.allowRemoteModels = false`、`env.localModelPath = '/models/'`，模型由本地服务同源提供，运行期无任何外部请求。

## 3. seekdb 使用

- **表结构**（seekdb-js 创建，逻辑等价）：

  ```sql
  CREATE TABLE kb_<name> (
    id VARCHAR(512) PRIMARY KEY,
    document TEXT,
    embedding VECTOR(512),
    metadata JSON,
    VECTOR INDEX (embedding) WITH (distance=cosine, type=hnsw, lib=vsag),
    FULLTEXT INDEX (document) WITH PARSER ik
  );
  ```

- **混合检索**：BFF 只调用一次 `collection.hybridSearch()`，seekdb 内部由 `DBMS_HYBRID_SEARCH` 生成并执行：

  ```sql
  SELECT ... FROM (
    (SELECT ... match(document) against(?) as _keyword_score ... ORDER BY _keyword_score DESC LIMIT 200) _fts
    FULL JOIN
    (SELECT ... cosine_distance(embedding, ?) ... ORDER BY _semantic_score DESC LIMIT 200) _vs
  )
  ... ORDER BY (1/(_keyword_rank+60) + 1/(_semantic_rank+60)) DESC;
  ```

  全文与向量两路候选的融合（RRF，k=60）完全在库内完成，客户端不接触单路结果；
- **写入与刷新**：每批 64 条 `add()` 后调用一次 `collection.refresh_index()`（对应 `CALL dbms_index_manager.refresh()`）。实测刷新前近似检索 0 命中、刷新后 3 命中，单批刷新约 520–700 ms；
- **增量与状态**：新文档追加到当前 collection，刷新后立即可检索；切换知识库时前端清空上一次结果并按新库重建查询；删除文档/集合后同步刷新并校验计数。

## 4. 状态管理与优化

- **集合/会话状态**：知识库列表与计数来自 BFF，当前库与查询历史保存在前端状态；`default` 库在首次启动时自动创建；集合名 `kb_<slug>` 与前端展示名一一对应；
- **批处理**：文档向量化 batch=8（WebGPU/WASM 均适用），写入 batch=64，每批一次 refresh，避免逐条刷新主导耗时；
- **性能对比**（同机、同语料，30 条查询平均）：

  | 配置 | 导入-向量化/篇 | 查询向量化 | seekdb 检索 | 端到端 |
  | --- | --- | --- | --- | --- |
  | FP32 + WASM | 86.7 ms | 25.5 ms | 8.7 ms | 44.6 ms |
  | FP16 + WebGPU | 45.1 ms | 30.8 ms | 9.0 ms | 50.3 ms |
  | INT8 + WASM | 57.6 ms | 17.3 ms | 10.0 ms | 38.0 ms |

- **其他优化**：模型文件走浏览器 HTTP 缓存；查询向量化与检索分离计时；结果渲染只展示 top-10 并高亮关键词。

> 设备：Windows 11 / Intel i7-14700HX / NVIDIA RTX 4070 Laptop；浏览器 Edge 156.0.4314.42；语料 20 篇、查询 30 条；计时包含内联的首轮开销，未做多轮预热取中位数（详见 `docs/benchmark.md` 的局限说明）。
